# 2026-04-12 M1.5：基于 context 使用率的记忆压缩

## 用户需求

> 按消息数压缩不是很合理，应该按 context 使用比例来压缩。

M1 的 token 预算管理用"裁剪最旧消息"做兜底，会丢失早期记忆。M1.5 在裁剪前先调 LLM 把旧消息压缩为摘要，让角色保持长期记忆。

## 现状

- `assemblePrompt` 已实现 token budget 管理，超出从最旧裁剪
- `aiConfigStore.summarizeAfter: number = 30` 按消息数触发，未实现，需改为比例触发
- `Conversation` 类型无 `summary` 字段
- ChatSettingsPage 有"自动摘要"滑杆，当前显示"每 N 条"

## 关键决策

### D1. 触发条件：token 比例 > 阈值

```
historyTokens / historyBudget > summarizeThreshold（默认 0.8）
```

在 `scheduleAICharacterReply` 里，`assemblePrompt` 返回后检查比例。超过阈值时后台调 LLM 生成摘要，存入 conversation。下次 assemblePrompt 时把 summary 作为 history 开头注入。

### D2. 摘要是异步后台任务

摘要调用不阻塞当前回复。流程：
1. 用户发消息 → assemblePrompt → streamChat（正常回复）
2. 回复结束后，检查 historyTokens / historyBudget
3. 超阈值 → 后台调 `compressHistory()` → 结果写入 `conversation.summary`
4. 下次发消息时 assemblePrompt 读到 summary → 注入 → 旧消息可以安全裁剪

### D3. 摘要注入位置

作为 history 的第一条 system message，格式：
```
[之前的对话摘要]
{summary content}
```

放在 chat history 最前面、system block 之后。这样模型先看到"背景"再看到最近的消息原文。

### D4. 增量更新

- 第一次压缩：所有超出预算的旧消息 → 摘要
- 后续压缩：把旧 summary + 新的被裁掉消息一起传给 LLM → 生成新 summary
- 这样 summary 不断滚动更新，不丢失更早的记忆

### D5. summarizeAfter → summarizeThreshold

- 类型从 `number` 改为 `number`（0-1）
- 默认值从 30 改为 0.8
- UI 从"每 N 条"改为百分比显示
- setter 限制 0-1 范围

### D6. compressHistory 用同一个 provider 和 model

摘要请求复用用户配置的 provider/endpoint/model/apiKey。不引入额外的模型配置。用非流式请求（不需要逐 token 展示）。
