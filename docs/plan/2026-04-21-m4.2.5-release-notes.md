# M4.2.5 Release Notes — Unified {type, param} Tool Wire Format

**Date:** 2026-04-21
**Status:** shipped
**Spec:** [docs/superpowers/specs/2026-04-20-m4.2.5-unified-tool-wire-format-design.md](../superpowers/specs/2026-04-20-m4.2.5-unified-tool-wire-format-design.md)
**Plans:** `docs/plan/2026-04-21-10{00,10,20}-m4.2.5-s{1,2,3}-*.md` (3 stages)

## What landed

### Wire format collapse

M4.2 had two top-level shapes — `{type:'text',content}` for narration and
`{type:'action',name,params}` for tool calls. M4.2.5 folds them into
one:

```json
{"type": "<tool-type>", "param": <any JSON value>}
```

`type` is the tool identifier (previously `name`); `param` is whatever
JSON value the tool declared (string / object / array / number / null).
The `text` tool is no longer special — apps register it like any other,
and pure-agent apps can omit it entirely.

### `ToolDefinition` reshape

```ts
// Before (M4.2):
interface ToolDefinition {
  name: string;
  description: string;
  parameters: Record<string, string>;
}

// After (M4.2.5):
interface ToolDefinition {
  type: string;
  description: string;
  param: string;  // prose hint: 'string (...)', '{...}', '[...]', or ''
}
```

### `parseReply` new signature + ParseError

```ts
export type ParseError =
  | { kind: 'not-json' }
  | { kind: 'wrong-shape' }
  | { kind: 'unknown-type'; badType: string };

export function parseReply(
  raw: string,
  knownTypes: ReadonlySet<string>,
): { items: ReplyItem[]; error: ParseError | null };
```

- Returns `{items, error}` — caller decides whether to retry
- `knownTypes` is the app's registered tool-type whitelist (empty Set disables check for renderer use)
- Mixed valid+invalid → whole-array rejection (no partial commit)

### Parse-error retry loop (new)

`ChatSession.send` / `replyToLast` now retry up to 3 times on parse
failure. Each failed attempt persists to memoryStore (`role:'assistant'`
with the raw bad output + `role:'system'` with a correction message
explaining what went wrong and listing valid types). The next retry's
prompt naturally includes these, so the LLM can self-correct.

On 3-attempt exhaustion:
- Platform calls `@hiphone/toast.show('AI 回复格式错误')` by default
- Apps providing `ChatOptions.onParseFailure` take over the UX (toast
  suppressed, callback fires with `{raw, attempts: 3}`)
- Session returns `ChatReply { items: [], rendered: '[生成失败]' }`

Failed-attempt memoryStore writes are **always** persisted — even when
the session was created with `mirror: false`. Otherwise the retry
prompt would be identical to the first attempt and the LLM would
repeat the same mistake.

### `ChatReply` simplification

```ts
// Before:
interface ChatReply {
  raw: string;
  rendered: string;
  items: ReplyItem[];
  actions: ReplyItemAction[];  // filter convenience
  text: string;                 // text-content concat convenience
}

// After:
interface ChatReply {
  raw: string;
  rendered: string;
  items: ReplyItem[];
}
```

Apps that want filtering do it themselves:
```ts
const texts = reply.items.filter((i) => i.type === 'text').map((i) => i.param as string);
const actions = reply.items.filter((i) => i.type !== 'text');
```

### Prompt chunks 7 & 8 updated

Chunk 7 (platform-hardcoded) is now a shorter single-shape template:
```
[回复格式]
你用 JSON 数组回复,每条是一个工具调用:
{"type":"<type>","param":<param>}

param 的形状由每个工具决定,详见 [可用动作]。

示例: [{"type":"text","param":"你好"},{"type":"sticker","param":{"stickerId":"s1","content":"笑"}}]

只输出 JSON 数组,不要其他内容。
```

Chunk 8 per-tool format:
```
[可用动作]
- text: 发一条聊天消息
  param: string (消息内容)
- sticker: 发一个表情包
  param: {stickerId: string, content: string}
```

### Renderer: `defaultXingYuRenderer` → `defaultReplyRenderer`

Renamed and simplified to two branches:
- `type === 'text'` AND `param` is string → `<speaker>: <param>`
- Everything else → `<speaker>: 【<type>】<JSON.stringify(param)>`

Every value survives in the rendered memory (lossless via JSON.stringify
for non-text), but the output is verbose for non-text:
```
小星: 【sticker】{"stickerId":"s1","content":"笑"}
```
vs M4.2's prettier `小星: [表情 s1: 笑]`. XingYu accepts the cosmetic
downgrade; apps that want pretty output register their own renderer.

### App migrations

- **XingYu** — registers 3 tools (text / sticker / update_signature),
  no custom renderer, app system-prompt keeps WeChat-style voice rules
  + dynamic sticker inventory. Bubble dispatch is now a `switch (item.type)`.
- **Auction fixture** — registers 4 tools (text + 3 actions), custom
  renderer kept to demonstrate per-app rendering, dispatch switches on
  `item.type`.

## Breaking changes

- `ReplyItemText` / `ReplyItemAction` / `ReplyItemSticker` / `ReplyItemSignature` types **removed**. Single `ReplyItem { type, param }` type replaces them.
- `ChatReply.actions` / `ChatReply.text` **removed**. Use `reply.items.filter(...)`.
- `ToolDefinition.name` / `.parameters` **renamed** to `.type` / `.param`.
- `DEFAULT_XINGYU_RENDERER` **renamed** to `DEFAULT_REPLY_RENDERER`.
- `defaultXingYuRenderer` module **renamed** to `defaultReplyRenderer`.
- Wire-format `{type:'action', name, params}` / `{type:'text', content}` no longer accepted — clean break.

## UX changes

### Auto-recovery from format errors

When the LLM messes up the format, users now see recovered replies more
often. On successful self-correction (1-2 bad attempts + good attempt):
- Response time is 2-4× longer than usual (extra LLM calls)
- memoryStore shows the full recovery trace — future prompts teach the
  LLM not to repeat the same mistake
- User sees only the successful bubbles (failed raws never become UI bubbles)

### Parse exhaustion fallback

After 3 attempts, the default platform toast `'AI 回复格式错误'` fires.
XingYu opted out of this (its own `[AI 回复失败]` chat bubble is
sufficient + less disruptive than a toast overlay). Other apps that
want custom UX use `ChatOptions.onParseFailure`.

### Cosmetic memory-text change

Sticker and action outputs in the memoryStore's rendered text now appear
verbose (`小星: 【sticker】{"stickerId":"s1","content":"笑"}`) vs M4.2's
pretty `小星: [表情 s1: 笑]`. Visible only in PromptViewerPage and
developer tooling — users never see this directly.
