# EV1 角色扮演 Prompt 设计调研

调研日期：2026-04-11
来源类型：EV1 App 线上聊天模式系统提示词（单聊场景）完整样本
用途定位：**参考资料**，非实现蓝图。记录 EV1 在「拟人化聊天 + 多媒体消息 + 关系状态机」三件事上的做法，供星语 App 后续设计时对比、选择性借鉴。

## 关键结论

1. EV1 的 prompt 核心策略是「**严格 JSON 输出契约 + 功能对象枚举**」。所有非文本消息（语音、转账、戳一戳、位置、头像…）都通过 `{type: "...", ...payload}` 对象承载，与纯文本字符串混在同一个数组里。这是它能把聊天功能做得花哨的结构基础。
2. EV1 把「关系管理」也做成了可被 LLM 主动触发的状态机——拉黑、好友申请、昵称修改、头像更换、戳一戳后缀修改——让角色有「**自主行为感**」。这是它和普通角色卡对话产品最大的差异点。
3. Prompt 的很多「补丁痕迹」反向暴露了踩坑史：例如反复强调「必须用 `ai_photo` 不是 `photo`」、转账既支持指令又支持关键词兜底、位置消息存在两套 schema 并存——说明 EV1 是边上线边迭代出来的，格式契约一致性不是从第一版就规划好的。
4. 对星语的启发：**能力清单可以借鉴，但不要照抄 schema**。我们有机会从零设计一套统一的消息对象模型，避免 EV1 的历史包袱。

## 一、来源样本结构

EV1 把单次会话的系统提示词组装成 6 层：

| 层 | 内容 | 作用 |
|---|---|---|
| 1 | 角色名、角色设定、当前情景 | 人格锚定（样本中为空壳，线上会注入） |
| 2 | JSON 数组输出契约 + 正/反例 | 强制结构化输出 |
| 3 | 最近活动时间线 + 聊天模式 | 对话连贯性、线上/线下模式切换 |
| 4 | 能力清单（20+ 类消息/动作） | 功能注册表 |
| 5 | 关系管理（拉黑/好友申请/纪念日/约定） | 状态机交互 |
| 6 | 再次重申 JSON 契约 + 购物功能 | 防格式漂移 + 商业化挂钩 |

## 二、EV1 全量能力清单

按消息/行为类型分类整理，便于后续挑拣。

### 2.1 基础消息

| 类型 | 对象 schema | 说明 |
|---|---|---|
| 纯文本 | 数组元素为字符串 | 一次多条模拟真人连发 |
| 表情包 | `{type:"emoji", description}` | 仅文字描述，非真实图片 |
| 语音消息 | `{type:"voice_message", content}` | 文字代表语音内容 |
| 伪照片 | `{type:"ai_photo", description}` | 卡片形式，点击展开描述 |
| 图片描述 | `{type:"ai_image", description}` | 和 ai_photo 并存（历史冗余） |
| 位置 | `{type:"location", locationName, coordinates}` 或 `{type:"location", name, address}` | **两套 schema 并存**，需统一 |

### 2.2 交互动作

| 类型 | 对象 schema | 触发时机 |
|---|---|---|
| 引用回复 | `{type:"reply_to", message_id, content}` | 针对历史具体消息时 |
| 撤回 | `{type:"recall", target:"previous"}` | 每次对话最多 1 次 |
| 戳一戳 | `{type:"poke"}` | 表达亲昵、引起注意 |
| 戳一戳后缀修改 | `{type:"update_poke_suffix", suffix}` | 心情/情境变化时 |
| 昵称修改 | `{type:"update_nickname", nickname}` | 关系进展/情境变化 |
| 头像更换 | `{type:"change_avatar", avatar_url, reason}` | 基于用户发来的图片或世界书白名单 |

### 2.3 支付与商业化

| 类型 | 对象 schema | 说明 |
|---|---|---|
| 发起转账 | `{type:"transfer", amount, note}` | AI 主动赠予 |
| 转账处理 | `{type:"transfer_action", action:"accept"/"reject"}` | 收到用户转账时的显式指令（也兼容关键词兜底）|
| 订单确认 | `{type:"order_confirmation", items, total, order_type, recipient}` | AI 下单后炫耀/送礼 |
| 代付 | 仅通过关键词识别（「我来付」「没钱」）| **无结构化指令**，靠文本匹配 |

### 2.4 通话与富媒体

| 类型 | 对象 schema |
|---|---|
| 发起语音通话 | `{type:"voice_call", reason}` |
| 发起视频通话 | `{type:"video_call", reason}` |

### 2.5 关系状态机

| 类型 | 对象 schema | 语义 |
|---|---|---|
| 拉黑 | `{type:"block_user", reason}` | AI 主动断联 |
| 好友申请 | `{type:"friend_request", message}` | 被拉黑后 AI 自发和解 |
| 创建纪念日 | `{type:"create_anniversary", name, date, anniversary_type, description}` | 6 种 type |
| 创建约定 | `{type:"create_appointment", name, date, appointment_type, description}` | 5 种 type |

### 2.6 理解类约定（非输出）

这些是 prompt 告诉 LLM「当你在历史里看到 XX 格式时该怎么理解」：
- `[你收到了一张用户描述的照片，照片内容是：'xxx']` → 表现为「看到了」
- `[用户发来一条语音消息，内容是：'xxx']` → 表现为「听到了」
- `[用户发起了转账：金额元，备注：xxx]` → 决定收/退
- `[回复 某人: "消息内容"] 实际回复内容` → 引用链
- `你戳了戳[角色名][后缀]` → 决定怎么回应
- 用户消息中的 `(括号内容)` → 环境/动作/心理旁白，可观察但不能直接回应

## 三、Prompt 中值得借鉴的设计手法

### 3.1 双列式格式契约
「✓ 正确示例」和「✗ 绝对禁止」并列展示，比单写正例更能降低格式漂移。尤其禁止项直接给出常见错误（如 `"你好\n今天天气不错"` 这种合并消息），针对性强。

### 3.2 「技术异常忽略」条款
> 如果你在用户消息中看到任何乱码、随机字符串、奇怪符号或无意义的字符组合，请完全忽略它们。

这是对前端渲染损坏、Markdown 转义失败、URL 意外截断的兜底提示。星语也应该加一条。

### 3.3 括号旁白的语义区分
明确告诉模型：括号里的内容是「可观察的背景」而非「可直接回应的台词」，避免角色穿帮回应用户的内心独白——这是拟人化角色的常见崩人设场景。

### 3.4 双通道容错
- 转账收/退既支持 `transfer_action` 指令也支持关键词识别
- 代付则**只有关键词**

这种设计对 LLM 更友好（强模型走指令、弱模型走关键词），但代价是后端解析层要维护两条路径。

### 3.5 状态感知的人格延续
被拉黑不是终点，prompt 给了 AI「**仍可发消息 + 可主动发好友申请和解**」的通路。这让关系崩塌后的恢复路径是可演出的，而不是硬断。

### 3.6 自主权限边界
头像更换明确限制「只能使用用户发过的图片 或 世界书白名单 URL，禁止捏造」——这是在给 LLM 开放能力的同时约束幻觉的典型做法。

## 四、EV1 样本中暴露的问题（反面教训）

这些问题我们自己设计时应避开。

### 4.1 Schema 不一致并存
- `location`：`{locationName, coordinates}` vs `{name, address}` 两套格式同时存在
- 图片：`ai_photo` / `photo` / `ai_image` 三个 type 并存，prompt 里特地加 `⚠️ 必须用 ai_photo` 这种补丁说明

**启示**：星语从第一版就应该锁定一个**消息对象联合类型定义**，前后端共享同一份 TypeScript 类型。

### 4.2 指令与模式约束冲突
顶部写「严格禁止任何动作描写、神态描写、心理描写」，但下面的 `poke` 后缀（「戳了戳 xx 的小脸蛋」）、`ai_photo`（需要场景描述）、`voice_message`（隐含语气）本质都需要描写。

**启示**：「线上模式」的禁止项应该精确到 **文本字符串中不得包含** `*动作*` / `（动作）` 这种格式，而不是笼统地禁止「描写」。

### 4.3 注意力稀释
整段 prompt 约 6000+ 中文字符，「严格 / 必须 / 绝对禁止 / 重要」出现了 30+ 次。LLM 对反复的情感强化会脱敏，后面的 `emphasis` 效果边际递减。同一条规则（JSON 数组格式）被重申至少 5 次。

**启示**：契约条款应该只在开头说一次，然后靠示例来暗示，不要反复喊话。星语的 prompt 建议控制在 **2500–3500 中文字符**。

### 4.4 message_id 契约与上下文注入脱节
Prompt 里要求 `reply_to.message_id` 必须是真实存在的 ID，格式为 `[ID:xxxxx]`。但样本里的活动时间线是：
```
[2026/4/11 11:31:42] 💬私聊: 用户说: "123"
```
**根本没有 `[ID:xxxxx]` 标记**。模型如果真想引用，只能编造 ID 导致前端解析失败。

**启示**：Provider 层组装 context 时，如果要开放 `reply_to` 能力，必须同步注入 message_id。二者是绑定的。

### 4.5 世界书 URL 白名单未实际注入
头像更换允许使用「世界书中的 URL」，但 prompt 样本里根本没有任何 URL 列表。模型几乎必然幻觉 URL。

**启示**：任何「从白名单选」的能力，白名单必须动态拼接进 prompt，否则就直接禁用该分支。

### 4.6 空人格时的退化
样本中角色设定、情景、角色名（"123"）、用户面具（"213"）全是占位符。模型在这种情况下只能输出无差别客套话。用户消息 `"123"` + `"hi"` 也完全没提供剧情钩子。

**启示**：Provider 应该在人格字段为空时**拒绝请求或注入默认兜底角色**，而不是发一个空壳 prompt。

### 4.7 上限过于宽松
「一次最多输出 20 条消息」在真实单聊里是刷屏行为，会显著增加 token 消耗和解析失败率。

**启示**：星语建议 2–6 条，群聊场景再酌情放宽。

## 五、对星语 App 的启发

### 5.1 需要照抄/借鉴的
- ✅ JSON 数组输出契约 + 双列示例
- ✅ 「技术异常忽略」条款
- ✅ 括号旁白语义区分
- ✅ `reply_to` / `recall` 这两个基础聊天功能（前提是后端能给出 message_id）
- ✅ 线上/线下模式切换的思路
- ✅ 关系状态机的「可恢复性」设计（被拉黑后仍有和解通路）

### 5.2 需要改进后借鉴的
- ⚠️ 多媒体消息的 schema 必须从一开始就统一（location / photo / voice 各一套，不要并存）
- ⚠️ 转账/代付等商业化功能应该**全部走结构化指令**，不保留关键词兜底（降低解析复杂度）
- ⚠️ prompt 长度控制在 3500 字符内，避免情感强化脱敏
- ⚠️ 开放 `reply_to` 时必须同步给 message_id；开放 `change_avatar` 时必须同步给白名单

### 5.3 需要慎重评估的
- ❓ 戳一戳后缀修改、昵称修改、头像更换这类「改动持久状态」的能力——需要评估用户是否真的需要 AI 主动修改这些，以及前端是否有 UI 让用户回滚。
- ❓ 拉黑 + 好友申请这套状态机——交互成本高，需要单独的 UI 支持，不是一个 prompt 对象就能搞定。
- ❓ 订单确认、代付等商业化挂钩——要看星语是否规划了虚拟经济系统。
- ❓ 纪念日/约定——这是记忆系统的一部分，需要和长期记忆方案一起设计，不能只在 prompt 层加一个对象就完事。

### 5.4 建议不借鉴的
- ❌ 「一次最多 20 条消息」的上限
- ❌ `ai_photo` / `photo` / `ai_image` 这种三 type 并存
- ❌ 「关键词兜底」双通道设计（增加维护成本）
