# M4.1 — AI SDK 消费端 + XingYu 迁移

## 概述

本期交付两件事：

1. **AI 记忆层解耦** —— 平台新增 `characterMemoryStore`，成为 AI 上下文的唯一来源。和任何具体 App 解耦（XingYu 只是其中一个写入来源）
2. **`@hiphone/ai` SDK 消费端** —— user app 可以调纯 AI（`complete` / `streamComplete`）和角色对话（session-based，支持 `persistent=true`/`false` 两种语义）

**同期做的一次性深度改造**：**XingYu 完全迁入 SDK**。XingYu 不再直接调 `assemblePrompt` / `chatComplete` / `collectCharacterHistory`，而是作为 SDK 的第一个消费者运行 —— 这也验证了 SDK surface 的完整性。

**设计原则：** AI 是一个"人"，它有自己的记忆；任何 App（包括 XingYu）和 AI 对话都往这份记忆里加内容；summarizer 对记忆统一压缩，不感知来源。

## 本期做 / 不做

**做：**
- `src/platform/ai/characterMemoryStore.ts` —— 按角色的对话记忆流，IDB 持久化
- `src/platform/userApp/sdk/ai.ts` —— `@hiphone/ai` 模块入口
- `complete` / `streamComplete` / `getCharacters`
- `chatWithCharacter(charId, { persistent })` 返回 `ChatSession`；session 方法：`send` / `streamSend` / `append` / `replyToLast` / `streamReplyToLast` / `history` / `abort`
- `buildMemoryEntry(msg, source)` —— 现有 `collectCharacterHistory` 的加工逻辑移为写时工具
- `promptAssembly` 的数据源换成 memoryStore（内部改造，签名不变）
- XingYu 所有写消息 action 双写 memoryStore；XingYu 的 AI 回复路径改为通过 session
- `summarizer` 的触发/存储改成 character-level（条目挂在 memoryStore，不再挂 Conversation）
- Demo user apps：`ai-translator-app`（`complete`）+ `ai-chat-app`（session）

**不做（明确推迟）：**
- 旧数据迁移 —— memoryStore 上线后从空开始；release note 标注"角色会失忆一次"
- Tool 系统 —— 属 M4.2 Tool Registry；heartbeat 继续走现有直接调用路径
- `aiChatEngine.runAIChat`（AI-AI 对话） —— 不迁移；继续直接调用
- Multimodal 图片/音频送模型
- 速率限制 / token 预算
- 用户可见的"AI 记忆查看器" UI（Settings）—— 未来工作

## 用户需求

**来自对话的关键引述：**

> "AI的记忆不应该和可爱信耦合，可爱信只是一个聊天App，而AI是一个人。任何App和AI的交流都可以写入AI的记忆，然后AI也会自动对这些信息进行压缩。"

> "persistent: false 是有clone语义，但是clone的目的是为了多次聊天，这个是否有合理的sdk设计。"

> "本期目标是完成 AI SDK 和将 xingyu直接接入 AI SDK。"

## 关键决策

| # | 决策 | 选择 | 理由 |
|---|---|---|---|
| D1 | 记忆是角色级还是会话级 | **角色级**（characterMemoryStore[charId]） | "AI 是一个人"；角色有一份统一记忆，不按 conv 划分 |
| D2 | XingYu 与记忆层关系 | 双写：xingYuDataStore 存富消息，memoryStore 存文本派生 | UI 数据 vs AI 数据职责分离；memoryStore 只存 AI 可读文本 |
| D3 | 旧数据迁移 | **不迁移** | 简化实现；接受 "AI 失忆一次" 的 UX 影响 |
| D4 | `persistent:false` 语义 | Clone 快照 + session 内部多轮累积 | 用户明确要求"clone 目的是多次聊天"；不要求 caller 手动维护 messages |
| D5 | Session 的形状 | 一个 JS object，`send` / `streamSend` / `append` / `replyToLast` / `streamReplyToLast` / `history` / `abort` | 能覆盖 XingYu 所有现有 AI 触发路径（文本 + 图/贴/转发后触发回复） |
| D6 | 回复落 memoryStore 的原子性 | user msg 先写；AI 回复仅在完成后写（abort/错误时不写 partial） | 避免"半句话"污染记忆；caller 想留 partial 用 `append` 显式 |
| D7 | AI 未配置的错误 | SDK 抛 `AIUnavailableError`；caller 处理 | SDK 通用；XingYu 在调用处 catch 并 fallback 到 `IDOL_REPLY_POOL` |
| D8 | heartbeat / AI-AI 对话迁不迁 | **不迁**；本期只迁 XingYu 普通文本/富消息链路 | 范围控制；heartbeat 留给 M4.2（Tool Registry 同期）；AI-AI 留给更后 |
| D9 | 压缩粒度 | character-level（不再 per-conv） | 和 D1 对齐；压缩结果是一条 MemoryEntry |
| D10 | Sandbox → memoryStore 的写权限 | 只通过 session 写；不暴露裸 memoryStore API 给 user app | 隐藏实现；caller 可见面是 session，不是 store |

## 架构

### 1. `characterMemoryStore`（平台层）

位置：`src/platform/ai/characterMemoryStore.ts`

```ts
export interface MemoryEntry {
  id: string;                    // uid
  characterId: string;
  role: 'user' | 'assistant' | 'system';
  content: string;               // 已加工的纯文本
  source:
    | 'xingyu'                   // XingYu 的 UI 写入镜像
    | `app:${string}`            // user app 通过 session 写入
    | 'heartbeat'                // heartbeat 工具写入的消息（M4.2 迁，本期兼容留位）
    | 'system';                  // summarizer 压缩结果、系统事件
  createdAt: number;             // Date.now()
  compressed?: true;             // 是否是压缩摘要条目
}

export interface CharacterMemoryState {
  entries: Record<string, MemoryEntry[]>;   // charId → 按 createdAt 升序
  
  append: (charId: string, entry: Omit<MemoryEntry, 'id' | 'createdAt'>) => MemoryEntry;
  batchAppend: (charId: string, entries: Omit<MemoryEntry, 'id' | 'createdAt'>[]) => MemoryEntry[];
  getAll: (charId: string) => readonly MemoryEntry[];
  getSnapshot: (charId: string) => readonly MemoryEntry[];   // 返回不可变拷贝（给 session 快照用）
  replaceRange: (charId: string, startId: string, endId: string, summary: MemoryEntry) => void;   // summarizer 用
  clear: (charId: string) => void;                           // 未来"AI 记忆查看器"用
}
```

**持久化：** IDB 通过 `idbRecordStorage`（和 xingYuDataStore.messages 同类型的 record store，按 entry 追加）。重启时从 IDB 恢复 `entries`。

**线程安全：** 所有写入走 Zustand action，单线程同步；并发 `append` 按调用顺序序列化。

### 2. `@hiphone/ai` SDK 表面

位置：`src/platform/userApp/sdk/ai.ts`

```ts
// ─── Level 1: 纯 AI ────────────────────────────────────────
export interface Message { role: 'system' | 'user' | 'assistant'; content: string }
export interface CompletionOptions { temperature?: number }

export function complete(
  messages: Message[],
  opts?: CompletionOptions,
): Promise<string>

export function streamComplete(
  messages: Message[],
  opts?: CompletionOptions & { signal?: AbortSignal },
): AsyncIterable<string>

// ─── Level 2: 角色会话 ────────────────────────────────────
export interface ChatOptions { persistent?: boolean; signal?: AbortSignal }

export function chatWithCharacter(
  characterId: string,
  options?: ChatOptions,
): ChatSession

export interface SessionEntry {
  role: 'user' | 'assistant'
  content: string
  timestamp: number
}

/**
 * 双写控制选项。只在 persistent=true 的 session 上有效。
 * - mirror=true (default): SDK 自动把这次操作涉及的 user/assistant 内容写入 memoryStore
 * - mirror=false: SDK 仅更新 session buffer；写 memoryStore 由 caller 自己负责
 * 
 * 场景：XingYu 内部流程已经自己往 memoryStore 写过一次（因为富消息要做 buildMemoryEntry），
 * 所以它调 session 时传 mirror=false 避免重复写入。user app 永远用默认 true。
 */
export interface MirrorOption { mirror?: boolean }

export interface ChatSession {
  readonly characterId: string
  readonly persistent: boolean
  readonly history: readonly SessionEntry[]

  send(content: string, opts?: MirrorOption): Promise<string>
  streamSend(content: string, opts?: MirrorOption): AsyncIterable<string>

  append(entry: { role: 'user' | 'assistant'; content: string }, opts?: MirrorOption): void

  replyToLast(opts?: MirrorOption): Promise<string>
  streamReplyToLast(opts?: MirrorOption): AsyncIterable<string>

  abort(): void
}

// ─── Level 3: 查角色 ──────────────────────────────────────
export interface CharacterInfo {
  id: string
  name: string
  avatar: string
  description: string
}

export function getCharacters(): CharacterInfo[]

// ─── 异常 ─────────────────────────────────────────────────
export class AIUnavailableError extends Error {}         // provider 未配置
export class AICharacterNotFoundError extends Error {}   // charId 无效
export class AIAbortedError extends Error {}             // session.abort() 之后被 await 的 promise
```

### 3. Session 行为细节

#### 3.1 创建

- 同步 capture 当前 appId（`getCurrentAppId()`）作为 `source=app:<id>`
- 校验 `characterId` 在 characterStore 中存在；否则抛 `AICharacterNotFoundError`
- 若 `persistent: false` —— 调 `memoryStore.getSnapshot(charId)` 拍一份快照到 session 私有字段
- 若 `persistent: true` —— 不拍快照；每次调用前读 memoryStore 最新版本

#### 3.2 `send(content)` / `streamSend(content)`

```
prompt = assemblePrompt({
  character: characterStore[charId],
  persona: personaStore.active,
  aiConfig: aiConfigStore,
  chatHistory: historyForSession(),   // 下方 3.6 解释
  newUserMessage: content,
})
→ chatComplete(stream)
→ if persistent:
    memoryStore.append({ role:'user', content, source: 'app:<id>' })
    await full reply
    memoryStore.append({ role:'assistant', content: reply, source: 'app:<id>' })
  else:
    session._buffer.push(user + assistant entries)
→ return reply / yield tokens
```

**abort 处理：** `streamSend` 过程中 `session.abort()` 被调用：
- user msg 已入库（persistent=true 场景）/ 入 session buffer（persistent=false）
- 已 yield 的 token 保留在 caller
- 未完成的 AI reply 不写入 memoryStore / session buffer
- 已 yield 的 AsyncIterable 停止产出，抛 `AIAbortedError`

#### 3.3 `append(entry)`

同步 push 到 session buffer；persistent=true 同时调 `memoryStore.append()`。**不触发 AI 调用。** 用于：
- XingYu `sendImageMessage` —— 先 `append({ role:'user', content:'[图片 <url>]' })` 然后 `streamReplyToLast()`
- caller 想塞一条 system note（目前不支持 role:'system'，reserved）

#### 3.4 `replyToLast(content)` / `streamReplyToLast(content)`

对当前 session state + memoryStore 上下文调 AI；回复按 persistent 规则落。不接受 user content（因为已经 append 过了）。

#### 3.5 `abort()`

取消当前 in-flight stream（AbortController）。不重置 session 状态。

#### 3.6 `historyForSession()` —— 内部辅助

- persistent=true：返回 `memoryStore.getAll(charId)` + session buffer 里还没入库的 entries（理论上是空，但如果 append 了一条但 replyToLast 还没发起时可能有）
- persistent=false：返回初始快照 + session buffer

### 4. 回复落 memoryStore 规则（完整表）

表中行为默认 `mirror: true`（用户 app 的默认）。**`mirror: false` 时这一整列 memoryStore 写入全部跳过**，只更新 session buffer —— caller 自己负责写。

| Session 方法 | persistent | 写 user msg | 写 AI 回复 |
|---|---|---|---|
| `send` / `streamSend(text)` | true | ✅ memoryStore, role=user, source=`app:<id>` | ✅ memoryStore, role=assistant |
| `send` / `streamSend(text)` | false | ❌ 仅 session buffer | ❌ 仅 session buffer |
| `append({ role, content })` | true | ✅ memoryStore, 按 role | — |
| `append({ role, content })` | false | ❌ 仅 session buffer | — |
| `replyToLast` / `streamReplyToLast` | true | — | ✅ memoryStore |
| `replyToLast` / `streamReplyToLast` | false | — | ❌ 仅 session buffer |
| abort (所有方法) | — | 已入库的 user msg 保留 | 未完成 reply 整条不写（无 partial 污染） |

**mirror=false 的唯一当前消费者：XingYu**。它在 §8.1 的流程里自己按"raw reply 一整条，不按 bubble 拆分"的规则写 memoryStore，是 SDK 没法替它做的。

### 5. `promptAssembly` 改造

- 签名不变（依然接受 `chatHistory`）
- 内部实现：`chatHistory` 来源从 `collectCharacterHistory(xingYuDataStore)` 换成 `memoryStore.getAll(charId).map(entryToHistoryMessage)`
- `entryToHistoryMessage(MemoryEntry) → HistoryMessage` —— 纯转换（memoryStore 已存文本，无需再加工）
- `collectCharacterHistory` 删除（所有调用方迁到 memoryStore）

### 6. `buildMemoryEntry(msg, source)`

纯函数，封装当前 `collectCharacterHistory` 里的加工逻辑：

```ts
// src/platform/ai/buildMemoryEntry.ts
export function buildMemoryEntry(
  msg: Message,                       // xingYuDataStore.Message
  source: MemoryEntry['source'],
  context: { charactersById: Map<string, Character>; personaName: string; userNickname: string },
): Omit<MemoryEntry, 'id' | 'createdAt' | 'characterId'> | null
```

输出的 `content` 是加工过的文本（quoteRef 展开 / forward_card 平铺 / 图片替换为 `[图片 <url>]` 等，同现有 `collectCharacterHistory`）。
返回 `null` 代表这条 msg 不入 AI 记忆（极少见，保留口子）。

### 7. Summarizer 改造

- **粒度从 conv-level 改为 character-level**：压缩目标是 `memoryStore.entries[charId]`
- 触发点：任何 `memoryStore.append` 之后检查该角色总 entries 的 token 数是否超过阈值 `summarizeThreshold × contextWindow`
- 压缩窗口：最旧的一批到 `entries.length - keepRecentMessages` 之间（不包含 already-compressed 条目）
- 结果：一条 `role: 'system', compressed: true, content: summary, source: 'system'` 的 MemoryEntry 替换被压缩的条目，通过 `memoryStore.replaceRange()` 完成
- Conversation schema 的 `summary` / `summaryUpToTimestamp` 字段 —— **删除**；迁移路径：启动时若还有残留不做处理（让它自然失效，因为 promptAssembly 不再读）

## XingYu 迁移（详细对照）

### 8.1 入口 action 映射：文本消息

XingYu 迁移走 session 但保留"自己负责往 memoryStore 写 xingyu-source 镜像"的职责（因为 XingYu 有自己的富消息 → 文本转换需求）。因此所有调用都用 `{ mirror: false }`：

```
XingYu.sendMessage(convId, text, quoteRef?):
  1. _appendMessage({ type:'text', text, quoteRef, senderId:'me', ... }, 'xingyu')
     → 内部：写 xingYuDataStore.messages[]；buildMemoryEntry → memoryStore.append(source='xingyu')
  2. session = chatWithCharacter(charId, { persistent: true })
  3. session.append({ role:'user', content: text }, { mirror: false })   // 只更新 session buffer，不重写 memoryStore
  4. const tokens = session.streamReplyToLast({ mirror: false })
  5. 累积 tokens 显示 typing 效果（可选）
  6. 流结束后取 session.history 最后一条 assistant content 作为 rawReply
  7. parseReply + filterReply(rawReply) → 多个 bubble
  8. 依次 _appendMessage(bubble, 'xingyu') 投递（保留 300-800ms 间隔）
       → 此时 memoryStore 追加的 assistant entry 是 rawReply（经过 filter 的单条）
         — 注意 memoryStore 只写一次（发生在 S8 的第一个 _appendMessage），不按 bubble 分条写
         — 这是有意的：AI 的"记忆"是它说的一整段，不是 UI 拆分后的 bubbles
```

**关键点：** `session.append/streamReplyToLast` 都用 `{ mirror:false }` —— XingYu 接管了 memoryStore 写入，因为它需要在 `filterReply` 之后才知道要往 memoryStore 写什么，而且 raw text 和 bubble 拆分结果不同。这是 `mirror` 选项存在的理由。

**user app 场景则相反：** `ai-chat-app` 调 `session.streamSend(text)` 不传 mirror，SDK 自动镜像；caller 不感知 memoryStore 存在。

### 8.2 各富消息 action

| Action | 新流程 |
|---|---|
| `sendImageMessage(convId, url)` | 1. 富消息追加 xingYuDataStore 2. `memoryStore.append({ role:'user', content:'[图片 <url>]', source:'xingyu' })` 3. `session.append({ role:'user', content:'[图片 <url>]' }, { mirror: false })` 4. `session.streamReplyToLast({ mirror: false })` 5. XingYu parse + render + 写 assistant 到 memoryStore |
| `sendStickerMessage` | 同上，content 为 `[表情：<stickerDesc>]` |
| `sendForwardCardMessage` | 同上，content 为当前 `collectCharacterHistory` 中展开后的 block |
| `sendNoteMessage` / `sendSongMessage` | 同上，按现有 `parseReply` 侧文本规则构造 content |

### 8.3 AI reply 渲染路径

当前：`scheduleAICharacterReply` 拿完整 reply → `parseReply` 解析成多个 bubble 对象 → 依次 `setState` 插入 `messages[]`（带 300-800ms 间隔）

迁移后：
```
for await (const token of session.streamReplyToLast({ mirror: false })) {
  // 可选：XingYu 内部累积 token，在 UI 上显示 typing 效果
}
// 流结束：session.history 的最后一条 assistant entry 是完整 raw reply
const rawReply = session.history[session.history.length - 1].content;
const parsedBubbles = parseReply(rawReply);
const filteredBubbles = parsedBubbles.map(filterReply);
for (const bubble of filteredBubbles) {
  xingYuDataStore.messages 追加；插入间隔保留
}
memoryStore.append({ role:'assistant', content: rawReply, source:'xingyu' });
```

XingYu 保留的 UI 层逻辑：`parseReply`（多 bubble 拆分）、`filterReply`（正则过滤）、multi-bubble delivery 间隔、typing 动画。

### 8.4 AbortController 管理

当前 `aiControllers: Map<convId, AbortController>` —— 迁移后变成 `aiSessions: Map<convId, ChatSession>`；取消改为 `session.abort()`。

### 8.5 Mock reply fallback

当前：`aiConfig` 无效 → XingYu 检测后走 `IDOL_REPLY_POOL`
迁移后：session.streamReplyToLast 抛 `AIUnavailableError` → XingYu catch → 继续 `IDOL_REPLY_POOL` 路径（和现在一样）。session 不尝试 mock —— 那是 caller 的 UX 决定。

### 8.6 Summarizer 触发

当前：`sendMessage` 末尾检查 `historyTokenRatio > summarizeThreshold` → `triggerCompression(convId)`
迁移后：**删除 XingYu 层触发**；memoryStore.append 内部检查并自动触发（每个 append 后 check + 异步压缩）。XingYu 无感知。

### 8.7 heartbeat / AI-AI 对话（读写策略）

**代码路径不迁：** `heartbeatAgent.runHeartbeat` 和 `aiChatEngine.runAIChat` 继续通过 `assemblePrompt` + `chatComplete` 直接调用，不走 session。行为与迁移前一致。

**读源统一：** S5 阶段把 `promptAssembly` 的数据源换成 memoryStore —— heartbeat / aiChat 间接受益，它们读到的历史和 XingYu session 读到的完全一致。

**写源统一（本期必须做，非 optional）：** XingYu 里任何 `setState({ messages: [...] })` 必须走私有 helper `_appendMessage(msg)`，该 helper 在更新 `xingYuDataStore.messages[]` 的同时调 `buildMemoryEntry` + `memoryStore.append(source='xingyu' | 'heartbeat')`。

- `sendMessage` / `sendImageMessage` / ... 已经是 action，内部改成调 `_appendMessage`
- heartbeatTools 的 `send_message` 当前直接 `setState`（为了避开 auto-reply loop）—— 改成调 `_appendMessage`，source 参数传 `'heartbeat'`
- `aiChatEngine.runAIChat` 的 AI-AI bubble 追加同理

这样 memoryStore 就是真实的"该角色下所有消息的并集"，M4.2 Tool Registry 迁过来时已经有完整的数据视图。

## 验收标准

1. `pnpm test` 全绿（预计 ~992 → ~1060+）
2. `pnpm build` 成功
3. 安装 `ai-translator-app` → 调 `complete` → 得到翻译结果
4. 安装 `ai-chat-app` → 多轮和角色对话（persistent=true）→ 关闭 app → 重开 → 角色"记得"之前对话
5. 安装 `ai-chat-app` → 多轮和角色对话（persistent=false）→ 关闭 app → 重开 → 角色**不记得**这个 app 里说过的话
6. XingYu 正常发消息（文本/图/贴纸/转发/note/song）→ AI 回复正常 + 多 bubble 分步投递保留 + typing 动画保留
7. XingYu 用户手动 cancel AI 回复 → 中止 + partial reply 不污染 memoryStore
8. 消息积累到 summarizeThreshold → 压缩自动触发 → memoryStore 被压缩条目替换
9. Heartbeat agent 继续正常运行（无行为变化）
10. AI 未配置 → user app `complete()` 抛 `AIUnavailableError`；XingYu 继续 `IDOL_REPLY_POOL` mock

- **M4.2 Tool Registry**：heartbeat 所有 tool 和 user app `aiTools` 都在 session 上暴露（`session.send` 支持 tool 流）

- **速率限制**：按 app 的 rolling window
