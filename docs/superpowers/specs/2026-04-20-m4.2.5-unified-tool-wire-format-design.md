# M4.2.5 — Unified `{type, param}` Tool Wire Format

## 概述

M4.2 把 Tool Registry 做起来了，但 chunk 7 仍然硬编码了两种顶级 shape——`{type:'text',content}` 和 `{type:'action',name,params}`——把 `text` 当作平台内置的特殊 primitive。

用户观察到：**`text` 本质就是一个工具，并不是所有 app 都需要**（翻译 app 只要 text、五子棋 bot 完全不要 text）。

本期把所有 AI 输出折叠到一个统一形状：

```json
{"type": "<工具名>", "param": <任意 JSON 值>}
```

`type` 即 tool 标识符（替换原 `name`），`param` 形状由每个工具自行声明（`string` / `object` / `array` / `number` / `boolean` / `null` 皆可）。`text` 不再特殊，和其他工具一样由 app 显式注册。平台代码因此更薄、跨 app 一致性更强。

同时加入 **parse 错误 → AI 重试**机制：最多 3 次，失败尝试全部落盘到 memoryStore，超过上限默认弹 toast（app 可覆盖）。

## 本期做 / 不做

**做：**

- `src/platform/ai/replyParser.ts` — 新 `parseReply(raw, knownTypes)` 签名，返回 `{items, error}`；新 `ParseError` 联合类型
- `src/platform/ai/toolRegistry.ts` — `ToolDefinition` 形状从 `{name, parameters: Record<string,string>}` 改为 `{type, description, param: string}`
- `src/platform/ai/promptAssembly.ts` — chunk 7 换新统一模板；chunk 8 的 tool line 渲染换成 `- ${type}: ${description}\n  param: ${param}` 格式
- `src/platform/ai/defaultXingYuRenderer.ts` → 改名并简化为 `defaultReplyRenderer`：文本走 `<speaker>: <param>`，其他走 `<speaker>: 【<type>】<JSON.stringify(param)>`
- `src/platform/userApp/sdk/ai.ts`
  - `ChatReply` 删除 `actions`、`text` 便利字段
  - `ChatSession.send` / `replyToLast` 加 **3 次 retry 循环**；失败写 memoryStore
  - `ChatOptions` 新增 `onParseFailure?: (info) => void`
  - 超过上限默认调 `@/platform/userApp/sdk/toast.show('AI 回复格式错误')`
- `src/apps/XingYu/xingYuRegister.ts` — 把 tools 全部按新 shape 注册，包括新增的 `text`
- `src/apps/XingYu/xingYuDataStore.ts` — bubble 分派从 `item.type === 'action'` 三叉改为按 `item.type` 直接 switch
- `src/platform/userApp/__tests__/fixtures/ai-auction-app/App.tsx` — 同样迁移
- 全部相关测试重写

**不做（明确推迟）：**

- Provider-native tool calling（OpenAI function calling / Anthropic `tool_use`）—— 留给 M4.3
- JSON Schema 校验 `param` 形状 —— `param` 是 prose hint，不做机器校验；形状不对由工具 handler 自己降级处理
- Heartbeat 迁入 Tool Registry —— 继续走 `formatOverride` path，M4.3 才动
- 任何老格式兼容层 —— 干净断裂（见下文风险窗口）

## 用户需求（对话原文截取）

> `{"type":"text","content":"..."}` 这个实际上也是一个工具 而非所有 app 都需要使用的

> 我希望现在就改,因此工具的 JSON 不再需要有 name 了,大家都是 type + param,param 可以是 object 可以是数组 可以是字符串都可以。

> 解析错误,错误是要返回给 AI 的,然后它会重试,这里最多重试 3 次。然后错误也会加到历史记录中。

> 3 次上限后的表现:默认弹系统 toast 提示,支持 app 自己实现。

## 关键决策

| # | 决策 | 选择 | 理由 |
|---|---|---|---|
| D1 | `text` 怎么安放 | **每个 app 自己注册 text 工具**（无平台内置常量） | 最纯粹——和其他 tool 零差异；每个 app 能给 text 写语境化描述；平台代码更薄 |
| D2 | 老格式兼容 | **干净断裂**（只认新 `{type, param}`） | memoryStore 存的是 rendered 文本而非 raw，无历史数据要回溯；升级瞬间 in-flight 响应降级为单条文本气泡 |
| D3 | Retry 触发条件 | a. 整段非 JSON / b. item 不是 `{type, param}` / c. 未注册的 `type` / e. 任一坏 item 整段 retry | 覆盖常见错误；param 形状不对（d）交给 tool handler 自己处理，不做机器校验 |
| D4 | 错误入历史的粒度 | **逐条写**：每次失败 assistant 原样 + system error 描述。**和 `mirror` flag 无关，失败总写入**（否则 retry 看到一模一样的 prompt,必然重复同样的错） | 长期记忆让 AI 学会自己的错误模式;debugging 友好;retry 有效 |
| D5 | `param` 声明形状 | **自由字符串（prose hint）**，由 LLM 理解；不做 schema 校验 | 简单、灵活、pattern 对齐 M4.3 的 JSON Schema 过渡 |
| D6 | Chunk 8 label | 沿用 `[可用动作]`（不改名为 `[可用工具]`） | 保持和 M4.2 术语一致；用户明确选这个 |
| D7 | `ChatReply.actions` / `.text` | **删除** | `text`/`action` 语义不再独立；app 要分拣自己 `items.filter(...)` |
| D8 | 默认 renderer | 单文件、单逻辑 `defaultReplyRenderer`；文本 vs 通用两分支 | 去掉 `defaultXingYuRenderer` 的 4 分支历史包袱；丑但一致 |
| D9 | 3 次失败后的默认 UX | 平台调 `@hiphone/toast.show('AI 回复格式错误')`；app 通过 `onParseFailure` 回调接管 | 大多数 app 默认就够；XingYu 这种有自己失败气泡的可传 no-op 抑制 |

## 架构

### 1. 统一 Wire 格式

每条 AI 输出是 `ReplyItem`：

```ts
export interface ReplyItem {
  type: string;        // 工具标识符,等于 ToolDefinition.type
  param: unknown;      // 形状由工具决定
}
```

整个回复永远是 `ReplyItem[]`（即便只有一条）。`raw` 里就是 JSON 数组：

```json
[
  {"type":"text","param":"你好"},
  {"type":"sticker","param":{"stickerId":"s1","content":"笑"}},
  {"type":"move","param":[3,5]},
  {"type":"pass","param":null}
]
```

### 2. `ToolDefinition` 新形状

```ts
export interface ToolDefinition {
  /** 工具标识符,对应 wire 格式的 type 字段(以前叫 name)。 */
  type: string;
  /** 对 LLM 的简短工具描述 */
  description: string;
  /**
   * param 形状的 prose hint（自由字符串,给 LLM 看的）。无参数工具传空串 `''`。
   * 示例:
   *   'string (消息内容)'
   *   '{stickerId: string, content: string}'
   *   '[x: number, y: number]'
   *   ''
   */
  param: string;
}
```

### 3. `parseReply` 新签名 + `ParseError`

```ts
export type ParseError =
  | { kind: 'not-json' }
  | { kind: 'wrong-shape' }
  | { kind: 'unknown-type'; badType: string };

export function parseReply(
  raw: string,
  knownTypes: ReadonlySet<string>,
): { items: ReplyItem[]; error: ParseError | null };
```

行为：

- 三级 fallback（直接 parse / 代码块 / bracket 提取）保留
- 第一个失败把 `error` 置位并短路返回
- `items` 只在 `error === null` 时有效；失败时 items 为 `[]`
- 调用方（session retry 循环）根据 `error` 决定是否重试

### 4. Session retry 循环

`ChatSession.send` / `replyToLast` 核心伪代码：

```ts
for (let attempt = 1; attempt <= 3; attempt++) {
  const raw = await callLLM(controller);
  if (controller.signal.aborted) throw new AIAbortedError();

  const knownTypes = new Set(frozenTools.map((t) => t.type));
  const { items, error } = parseReply(raw, knownTypes);

  if (error === null) {
    // 成功路径
    const rendered = renderer.render(raw, ctx);
    doAppend({ role: 'assistant', content: rendered, speakerId: characterId }, mirror);
    return { raw, rendered, items };
  }

  // 失败 — 两条 entry 一起写(D4: 逐条写)
  //
  // NOTE: 失败尝试总是写入 memoryStore,**和 mirror flag 无关**。
  // 如果不写,下一轮 retry 的 prompt 会和本轮完全一致,LLM 没有任何线索
  // 修正上次的错误,必然会重复同样的错。mirror:false 语义只控制
  // **成功路径**的 assistant 条目是否镜像,不管失败路径。
  useCharacterMemory.getState().append(characterId, {
    role: 'assistant', speakerId: characterId, content: raw, source,
  });
  useCharacterMemory.getState().append(characterId, {
    role: 'system', speakerId: 'system', content: buildErrorMessage(error, frozenTools),
    source: 'system',
  });
  // 循环,下一轮 prompt 从 memoryStore 重新装配时会自然包含这两条
}

// 3 次都失败 — 超过上限(同样不管 mirror)
useCharacterMemory.getState().append(characterId, {
  role: 'system', speakerId: 'system', source: 'system',
  content: '[格式错误] AI 3 次回复格式均不合法,已放弃重试',
});

if (options.onParseFailure) {
  options.onParseFailure({ raw: lastRaw, attempts: 3 });
} else {
  // 默认 UX — 平台级 toast
  platformToast.show('AI 回复格式错误');
}

return {
  raw: lastRaw,
  rendered: '[生成失败]',
  items: [],
};
```

### 5. 错误消息模板

```ts
function buildErrorMessage(error: ParseError, tools: ToolDefinition[]): string {
  const typeList = tools.map((t) => t.type).join(', ');
  switch (error.kind) {
    case 'not-json':
      return '[格式错误] 上条回复不是合法 JSON。你必须只输出 JSON 数组,形如 ' +
             '[{"type":"<type>","param":<param>}],不要任何其他文字。';
    case 'wrong-shape':
      return '[格式错误] 上条回复不符合 {type, param} 结构(有 item 缺少 type 或格式不对)。' +
             '请按 [回复格式] 要求重新输出 JSON 数组。';
    case 'unknown-type':
      return `[格式错误] 你使用了未注册的 type "${error.badType}"。` +
             `当前可用 type 只有: ${typeList}。请只使用这些。`;
  }
}
```

### 6. 新 Chunk 7（平台硬编码）

```
[回复格式]
你用 JSON 数组回复,每条是一个工具调用:
{"type":"<type>","param":<param>}

param 的形状由每个工具决定,详见 [可用动作]。

示例: [{"type":"text","param":"你好"},{"type":"sticker","param":{"stickerId":"s1","content":"笑"}}]

只输出 JSON 数组,不要其他内容。
```

硬编码、跨 app 字节稳定。

### 7. 新 Chunk 8 渲染

```ts
function buildToolsChunk(tools: ToolDefinition[]): string | null {
  if (tools.length === 0) return null;
  const lines = tools.map((t) => {
    const paramLine = t.param ? `\n  param: ${t.param}` : '';
    return `- ${t.type}: ${t.description}${paramLine}`;
  });
  return `[可用动作]\n${lines.join('\n')}`;
}
```

示例输出（XingYu 注册后）：

```
[可用动作]
- text: 发一条聊天消息,像真人发微信
  param: string (消息内容)
- sticker: 发一个表情包。stickerId 必须从 [当前任务] 中列出的可用表情里选
  param: {stickerId: string, content: string (表情简短描述)}
- update_signature: 修改个性签名,不要频繁更换
  param: {text: string}
```

### 8. `defaultReplyRenderer`（原 `defaultXingYuRenderer`）

改名 + 简化：

```ts
// src/platform/ai/defaultReplyRenderer.ts
export const defaultReplyRenderer: ReplyRenderer = {
  render(raw, ctx) {
    const { items } = parseReply(raw, new Set()); // 渲染不做 knownType 校验
    return items
      .map((item) => {
        if (item.type === 'text' && typeof item.param === 'string') {
          return `${ctx.speakerName}: ${item.param}`;
        }
        const paramStr =
          typeof item.param === 'string' ? item.param : JSON.stringify(item.param);
        return `${ctx.speakerName}: 【${item.type}】${paramStr}`;
      })
      .join('\n');
  },
};
```

**产出示例**：
- `[{type:'text', param:'你好呀'}]` → `小星: 你好呀`
- `[{type:'sticker', param:{stickerId:'s1',content:'笑'}}]` → `小星: 【sticker】{"stickerId":"s1","content":"笑"}`
- `[{type:'move', param:[3,5]}]` → `小星: 【move】[3,5]`
- 无 item 时 → 空串

**丑但一致**：LLM 读自己的历史时是"我调用了什么工具、参数是什么"的统一叙述，不需要识别多种特殊格式。

`replyRendererRegistry.DEFAULT_XINGYU_RENDERER` 重命名为 `DEFAULT_REPLY_RENDERER`，并 re-export `defaultReplyRenderer`。

### 9. `ChatReply` 精简

```ts
export interface ChatReply {
  /** LLM 字节原文 */
  raw: string;
  /** 经 renderer 后的自然文本(写入 memoryStore 的那份) */
  rendered: string;
  /** parseReply 拆好的 items,按原顺序 */
  items: ReplyItem[];
  // 删除:actions, text
}
```

App 想做便利分拣自己写一行：

```ts
const texts = reply.items.filter((i) => i.type === 'text').map((i) => i.param as string);
const bids = reply.items.filter((i) => i.type === 'bid_call');
```

### 10. `ChatOptions` 新增 `onParseFailure`

```ts
export interface ChatOptions {
  persistent?: boolean;
  signal?: AbortSignal;

  /**
   * 当 AI 连续 3 次回复格式均不合法、session 放弃重试后调用。
   *
   * 不传 → 平台默认 `toast.show('AI 回复格式错误')`
   * 传任何函数(包括 `() => {}`)→ 平台不弹 toast,由 app 全权负责
   */
  onParseFailure?: (info: { raw: string; attempts: number }) => void;
}
```

在 `sdk/ai.ts` 顶部导入：

```ts
import { show as showToast } from './toast';
```

3-次上限后不带 callback 的分支调 `showToast('AI 回复格式错误')`。

## Legacy 数据

memoryStore 在 M4.2 写入的 assistant 条目是**已渲染自然文本**，不是 raw JSON——这些在新解析器下不会被再解析，仅作为历史上下文发给 LLM。**完全不需要迁移**。

例如老的 `小星: 【bid_call】item=lot-1 min=500` 和新的 `小星: 【bid_call】{"item":"lot-1","min":500}` 在历史里并存也没问题，LLM 两种形式都看得懂。

## 风险窗口

升级瞬间**仍在路上**的 LLM 响应是老 prompt 发出的，回来的 JSON 是老 shape（`{type:'text',content}`）。新 `parseReply` 遇到会判 `wrong-shape` → retry 循环。因为新 prompt 已经用新 chunk 7/8，LLM 下一轮自然按新格式回 → 成功。

观察：**最坏一次用户对话有一次"首包 retry 一次"的延迟**，之后一切正常。可接受。

## 验收标准

1. `pnpm test` 全绿（预计 M4.2 基线 1158 +/- ≤20）
2. `pnpm typecheck` 清洁；`pnpm build` 成功
3. 所有 `reply.actions` / `reply.text` 的调用点删除（grep 验证）
4. XingYu 注册的 tools 数量从 2 升到 3（加了 `text`）
5. Auction fixture 注册的 tools 数量从 3 升到 4（加了 `text`）
6. 新 `parseReply` 不再接受老 shape（`{type:'text',content}` 等），会返回 wrong-shape error
7. session 重试逻辑可观察：mock `chatComplete` 前 2 次返回坏 raw、第 3 次好 raw → session 成功返回第 3 次的 ChatReply，memoryStore 恰好包含 2 条 assistant(坏 raw) + 2 条 system(error msg) + 1 条 assistant(rendered)
8. 3 次都失败时：默认 `toast.show('AI 回复格式错误')` 被调用一次（无 onParseFailure 的情况）
9. 提供 `onParseFailure` 时：toast **未**被调用，callback 被调用恰好一次
