# 五子棋 AI 角色对弈设计

日期: 2026-04-30

## 1. 用户需求

用户希望将现有五子棋 App 从“和代码 AI 玩”改成“和 AI 角色玩”。AI 角色必须真正参与棋局决策，而不是只作为本地算法外层的聊天皮肤。对局过程中，用户可以边下棋边和角色聊天，AI 角色也可以在下棋时说话。

已确认的关键需求:

- 五子棋只使用设置中已有的 AI 角色，不内置专属棋手角色。
- 正式入口只保留“和 AI 角色下棋”，旧的本机双人和代码 AI 模式不作为正式入口保留。
- 本地代码 AI 只作为 AI 角色连续 3 次未给出合法落子后的降级兜底。
- 用户可选择自己执黑或执白；如果用户执白，AI 角色先手。
- 右上角“新局”表单负责选择角色和先手，默认沿用上次配置。
- 没有任何 AI 角色时，五子棋显示空状态，引导用户到设置创建角色。
- 用户点棋盘立即落子并触发 AI 棋局回合。
- 输入框发送纯聊天，纯聊天不改变执棋方，也不触发 AI 落子。
- AI 棋局回合必须下棋，可选聊天；AI 纯聊天回合只回复文字，不下棋。
- 每一步落子事件都写入角色长期记忆。
- 当前完整棋盘矩阵每次注入 prompt 尾部，但不写入长期记忆。
- 用户头像需要在顶部双方身份区和聊天气泡中展示，形成“用户和角色面对面下棋”的感觉。

## 2. 推荐方案

采用“方案 A: 五子棋作为独立 AI 角色会话 App”。

五子棋自己注册 AI 工具、维护棋局状态、渲染聊天面板和处理重试降级；角色、长期记忆、prompt 组装、LLM 请求与工具解析复用平台现有 AI 基础设施。这样五子棋不会被可爱信的数据结构绑定，同时 AI 角色确实通过五子棋工具完成落子和聊天。

## 3. 产品体验

五子棋打开后直接进入当前/最近一次角色对局。若已有角色但没有对局，进入可开始新局的空棋盘状态。若没有任何角色，显示 iOS 设置风格空状态，文案引导用户前往“设置 → 角色”创建角色。

主界面采用固定分屏:

- 上半屏: 棋盘、当前手数、执棋状态、双方身份和比分。
- 下半屏: 聊天流、输入框、AI typing/thinking 状态。

顶部身份区显示两位玩家:

- 用户侧: 用户头像、名称“你”、黑/白棋子标识、分数。
- AI 侧: 角色头像、角色名、黑/白棋子标识、分数。

聊天面板遵循 iOS Messages 语义:

- 用户消息靠右，显示用户头像。
- AI 消息靠左，显示角色头像。
- AI 思考时显示轻量 typing/thinking indicator。
- 输入框只用于纯聊天，不承担落子确认。

落子交互:

- 用户点击合法空点后立即落子。
- 若本手产生胜负，结束本局并写入记忆。
- 若未结束，立即触发 AI 棋局回合。
- 用户在输入框发纯聊天时，只触发 AI 纯聊天回复，不改变棋盘和执棋方。

新局入口:

- NavBar 右侧提供“新局”按钮。
- 打开 `NewGameSheet`，选择角色、选择用户执黑/白。
- 开始新局会重置棋盘、聊天流的本局上下文和 AI 运行状态；历史比分保留为用户胜场数和 AI 胜场数。

## 4. AI 工具协议

五子棋内部工具协议采用统一 `{ type, param }` 数组。

```json
[
  { "type": "text", "param": "自然语言聊天内容" },
  { "type": "place_stone", "param": { "row": 7, "col": 8 } }
]
```

工具定义:

- `text`: 可选。渲染为聊天气泡。UI 叫“聊天”，协议保留 `text`，对齐平台现有工具约定。
- `place_stone`: 棋局回合必选，纯聊天回合禁止。`row` / `col` 使用 0-based 数字坐标，范围 0 到 14。

棋局回合合法性:

- 输出必须是可解析的 JSON 数组。
- 必须包含且只处理一个 `place_stone`。
- `row` / `col` 必须是整数。
- 坐标必须在 15x15 棋盘内。
- 目标位置必须为空。
- 当前必须轮到 AI 执棋。

纯聊天回合合法性:

- 必须输出至少一个 `text`。
- 禁止 `place_stone`。
- 若 AI 在纯聊天回合输出 `place_stone`，忽略该落子并将其视为格式错误重试。

## 5. Prompt 设计

每次 AI 请求都构建为角色对话请求，并在 prompt 尾部注入五子棋运行态。尾部状态只用于当前请求，不进入长期记忆。

尾部状态包含:

- 当前 App: 五子棋。
- 本局角色: AI 角色名、AI 执棋颜色、用户执棋颜色。
- 当前轮次: 棋局回合或纯聊天回合。
- 当前棋盘: 15x15 矩阵，固定使用 `.` 表示空位、`B` 表示黑棋、`W` 表示白棋。
- 最近若干手: 用 UI 坐标辅助模型理解，例如 `H8 黑`，但协议仍只接受数字 `row/col`。
- 当前轮到谁。
- 合法输出格式。
- 棋局回合必须输出 `place_stone` 的硬性规则。
- 纯聊天回合禁止输出 `place_stone` 的硬性规则。
- 第一版标准五子棋规则: 五连胜；暂不实现复杂禁手。

尾部棋盘状态不写入长期记忆，避免角色记忆被完整矩阵刷屏。长期记忆只写事件事实。

## 6. AI 重试与降级

AI 棋局回合最多重试 3 次。

触发重试的情况:

- 回复无法解析。
- 缺少 `place_stone`。
- `place_stone` 参数格式错误。
- 坐标越界。
- 目标格已被占用。
- 在纯聊天回合输出 `place_stone`。

每次重试都向模型追加本轮错误原因和修正要求，让角色重新输出合法工具数组。3 次仍失败时，使用现有 `getAIMove(board, aiStone)` 代走。

降级代走必须透明呈现:

- UI 聊天流显示系统气泡，说明“角色未能给出合法落点，系统代走 X”。
- 长期记忆写入该事实，不假装是角色本人成功下出。
- 棋盘仍正常推进，避免整局卡死。

## 7. 状态模型

`gomokuStore` 从简单 `pvp/pve` 模式升级为角色对局会话模型。

核心状态:

- `board`: 15x15 棋盘。
- `moves`: 本局落子序列。
- `currentPlayer`: 当前执棋颜色。
- `userStone`: 用户执棋颜色。
- `aiStone`: AI 执棋颜色。
- `characterId`: 当前 AI 角色 id。
- `result`: 胜负结果和胜利线。
- `scores`: 用户胜场数和 AI 胜场数。
- `messages`: 五子棋本局聊天流。
- `aiStatus`: idle / thinking / retrying / failed / fallback。
- `lastError`: 最近一次 AI 错误信息。
- `gameId`: 当前局 id，用于消息和记忆事件关联。

持久化:

- 继续使用 `hiPhone-gomoku` 存储名。
- 持久化棋盘、当前玩家、角色 id、用户颜色、消息、比分和结果。
- 不持久化运行中的 AbortController、timer、in-flight session。

恢复:

- UI 从五子棋 store 恢复当前局。
- 下一次 AI 请求时重新从 store 构造棋盘尾部 prompt。
- 角色长期记忆提供叙事上下文，但不作为棋盘事实源。

## 8. 记忆写入

按用户选择，每一步落子事件都写入角色长期记忆，但不写完整矩阵。

写入示例:

- `用户在 H8 落黑。`
- `凛在 I8 落白。`
- `用户说：“你这步有点凶。”`
- `凛说：“我先压住你的活三。”`
- `凛在 J8 落白，并说：“我先压住你的活三。”`
- `凛三次没有给出合法落点，系统代走 J8。`
- `本局结束：用户黑棋获胜。`

记忆边界:

- 棋盘矩阵不进入记忆。
- prompt 尾部运行态不进入记忆。
- 纯聊天写入记忆。
- 非法落子重试和系统代走写入记忆。
- 胜负结果写入记忆。

## 9. 组件拆分

建议文件边界:

- `GomokuApp.tsx`: 页面组装、NavBar、新局入口、空状态、AI 状态协调。
- `GomokuBoard.tsx`: 棋盘渲染、点击落子、最后一步、胜利线。
- `GomokuChatPanel.tsx`: 聊天流、头像、输入框、typing indicator。
- `NewGameSheet.tsx`: 角色选择、用户执黑/白、新局确认。
- `gomokuStore.ts`: 棋局状态、落子规则、胜负判断、持久化。
- `gomokuAiSession.ts`: prompt 构建、AI 请求、回复解析、重试、降级。
- `gomokuRegister.ts`: 五子棋工具注册、app system prompt、reply renderer。
- `gomokuMemory.ts`: 落子/聊天/失败/胜负事件写入角色记忆。

`GomokuBoard` 不直接知道 AI 角色和聊天，只暴露点击落子的 UI 行为。`gomokuAiSession` 不直接操作 DOM，只接收 store 快照和 dispatch 回调。这样棋局规则、AI 协议和 UI 可以分别测试。

## 10. 测试策略

单测优先覆盖:

- 创建空棋盘、合法落子、非法重复落子。
- 五连胜检测和胜利线。
- 用户执黑/执白初始化。
- 用户执白时 AI 先手触发。
- 用户点击棋盘立即落子并进入 AI thinking。
- 纯聊天不会落子、不会切换当前玩家。
- AI 棋局回合缺少 `place_stone` 会重试。
- AI 落到已占位置会重试。
- 三次非法落子后调用本地 `getAIMove` 代走。
- `text + place_stone` 可以同时渲染聊天并落子。
- 棋盘矩阵出现在 prompt 尾部。
- 棋盘矩阵不写入角色记忆。
- 每一步用户/AI 落子事件写入角色记忆。
- 没有角色时显示空状态。

UI 测试覆盖:

- 新局表单选择角色和先手。
- 顶部双方身份区展示用户头像和 AI 头像。
- 聊天气泡展示双方头像。
- AI thinking/retrying/fallback 状态文案。

## 11. 里程碑建议

该需求涉及棋局状态、AI 工具、记忆、UI 和测试，建议拆成多个阶段实施，每阶段对应独立 `docs/plan/yyyy-mm-dd-hhmm-计划名.md`。

第一阶段: 状态模型与 UI 骨架

- 重构 `gomokuStore` 为角色对局模型。
- 新增 `NewGameSheet` 和 `GomokuChatPanel`。
- 实现头像展示、固定分屏和无角色空状态。
- 保持 AI 调用先不接入，先用测试覆盖状态和 UI。

第二阶段: AI 工具与 prompt

- 注册 `text` / `place_stone` 工具。
- 构建棋盘尾部 prompt。
- 通过 `chatWithCharacter` 接入角色会话。
- 实现棋局回合和纯聊天回合的不同约束。

第三阶段: 重试、降级和记忆

- 实现三次重试。
- 接入本地 `getAIMove` 降级。
- 写入角色长期记忆。
- 补齐 prompt/记忆边界测试。

第四阶段: 体验 polish

- 动画、状态文案、错误提示、触感反馈。
- 棋盘和聊天分屏在不同屏幕尺寸下的适配。
- 用浏览器截图验证头像、文字和棋盘不重叠。

## 12. 非目标

第一版不做:

- 本机双人正式入口。
- 本地代码 AI 正式模式入口。
- 内置专属棋手角色。
- 五子棋复杂禁手规则。
- 多角色观战或群聊下棋。
- AI 主动提出新局。
- 流式工具调用或真正多轮 tool-call 协议。

## 13. 关键决策记录

- 选择现有角色系统，而不是内置棋手角色。
- 选择固定分屏，而不是棋盘抽屉或聊天流主屏。
- 用户点棋盘立即落子，输入框只做纯聊天。
- 每一步落子写入长期记忆。
- 棋盘矩阵只进 prompt 尾部，不进记忆。
- 用户可选执黑/执白。
- 新局表单放在右上角入口。
- 旧模式不保留正式入口。
- 无角色时引导去设置创建角色。
- 协议内部使用 `text`，UI 仍叫聊天。
- AI 失败三次后降级为代码 AI，并透明写入记忆。
- 用户头像必须和 AI 头像一样成为主界面身份信息的一部分。
