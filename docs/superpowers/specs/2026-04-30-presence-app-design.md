# 「在场」App 设计规格

## 概述

「在场」是一个现场式 AI 角色互动 App。它不把 AI 放在聊天软件的消息气泡里，而是让用户选择一个角色和一个具体场景，然后进入一段像小说现场一样的互动。

App 的核心不是“离线”或“无网络”，也不是 AR。核心是 presence：角色此刻就在某个场景里，面对玩家说话、停顿、移动、观察、做出表情、触碰环境，或者主动提出符合角色和场景的行为。

推荐名称：

- 用户可见名：`在场`
- 内部 appId：`presence`
- 功能描述：`现场式角色互动`

备选名：

- `此间`：更文学，但语义略抽象。
- `入境`：强调进入场景，但偏工具感。
- `近处`：有陪伴感，但不如“在场”准确。

最终建议使用「在场」。

## 用户需求

来自 2026-04-30 的对话需求：

- 不要叫“线下模式”这种直白名字。
- 打开 App 后能选角色。
- 能选场景，场景支持用户自定义输入。
- 进入场景后开始现场式互动。
- 用户仍然可以像聊天一样输入，但 AI 的输出不只是聊天文字。
- AI 应自由包含动作、眼神、神态、表情、姿态、环境互动和主动行为。
- 不要给 AI 定死输出协议，不要要求固定 JSON 字段。
- 系统要告诉 AI：它已经不是在聊天软件里，而是在某个场景下和玩家面对面互动。
- 用户可以随时离开。
- 场景进行中的互动不实时写入长期记忆。
- 用户完成或退出后，把本次场景经历总结后写入 AI 记忆。
- 记忆写入模式类似自主活动：经历本身在过程中发生，结束后作为总结进入记忆。

2026-05-01 设计稿修订需求：

- 用户可见文案不要写“AI 角色”，统一写“角色”。
- 角色列表当前只显示头像和名字，不展示关系、上次活动、最近互动等不存在字段。
- 场景可以自定义输入，也可以选择预设场景。
- 背景图由 App 自带预设图库解决；选择预设场景时用绑定图片，自定义场景时随机选一张兜底图。
- 场景页不要出现含义不清的“场景笔记”。
- 明确互动内容生成逻辑：AI 按现场式 prompt 自由生成小说式片段，UI 只做展示和弱样式。
- 离开页保持四项摘要，但去掉“记忆价值”这种当前系统没有的概念。
- 完成后的在场记录需要保存，之后可查看；已完成记录只能看，不能继续互动。

## 产品定位

「在场」不是 XingYu 的替代品。

- XingYu：消息式聊天，重点是即时通讯、气泡、图片、表情、转发、朋友圈等社交软件范式。
- 在场：现场式互动，重点是场景、角色当前存在感、非语言描写和小说式连续片段。

用户仍然可以输入文字，但交互心智不再是“我发一条消息，AI 回一条消息”，而是“我在这个地方和这个角色一起发生一段场景”。

## 信息架构

### 入口首页

首页使用 iOS 风格导航：

- 顶部居中标题：`在场`
- 主区域分两步：
  - 选择角色
  - 选择场景
- 底部主按钮：`进入场景`

### 角色选择

角色来自现有角色列表。用户可见文案只使用“角色”，不写“AI 角色”。

列表展示：

- 角色头像
- 角色名
- 最近进入过的角色排在前面

V1 不展示关系、上次活动时间、最近互动摘要、角色简介等字段，因为当前角色数据没有这些稳定字段。列表必须保持轻量，避免用不存在的数据做假 UI。

V1 不需要创建角色；创建和管理仍沿用现有角色系统。

### 场景选择

场景必须支持用户自由输入，这是核心能力。

场景输入区域：

- 多行输入框。
- placeholder：`例如：雨夜的便利店门口，她撑着伞站在灯下等你。`
- 支持保存最近使用的场景。
- 可提供少量快捷场景，但不能喧宾夺主：
  - `傍晚的天台`
  - `深夜厨房`
  - `雨中的公交站`
  - `安静的图书馆`
  - `回家路上`

场景不是枚举，快捷场景只是填充输入框的模板。

### 背景图策略

V1 不依赖实时生成背景图，也不要求用户上传图片。App 内置一批 `PresenceBackdrop` 预设背景图。

预设场景和背景图绑定：

- `傍晚天台` → 天台黄昏背景
- `深夜厨房` → 暖色厨房背景
- `雨中便利店` → 雨夜街边/便利店灯光背景
- `安静图书馆` → 图书馆窗边背景
- `回家路上` → 夜晚街道路灯背景

自定义场景：

- 用户输入任意场景文本。
- 系统从预设背景图库中随机选择一张兜底图。
- V1 不需要语义匹配；后续可以根据关键词选择更接近的背景。
- 背景图只是氛围，不代表用户输入场景被强制改写。

```ts
interface PresenceBackdrop {
  id: string;
  title: string;
  imageUrl: string;
  presetSceneId?: string;
}
```

### 场景会话页

场景页不是 chat bubble 列表，而是“现场片段流”。

布局：

- 顶部导航栏：
  - 左侧返回箭头
  - 居中标题：场景短标题，优先从用户输入生成或截断
  - 右侧：`离开`
- 主视觉区：
  - 角色头像或半身像
  - 当前角色名
  - 当前场景一句话
  - 背景使用预设图库图片；自定义场景使用随机兜底图
- 片段流：
  - AI 回复以小说段落展示，不使用消息气泡。
  - 用户输入可以用较轻的“你……”行展示，保留上下文连续性。
  - 括号内非语言描写可做浅色/斜体/较小字号样式，但不强制模型使用括号。
- 输入区：
  - placeholder：`说点什么，或写下你的动作…`
  - 用户可以输入台词，也可以输入动作，例如：`我走到她旁边坐下。`
  - 发送按钮使用 iOS 图标按钮。

场景页不展示“场景笔记”。如果需要给用户看当前场景，只在主视觉区展示场景一句话；片段流专注于互动本身。

## AI 行为设计

### 核心 prompt 心智

「在场」的 prompt 重点不是格式，而是身份切换：

```text
你现在不是在聊天软件里回复消息。
你正处在一个具体场景中，和玩家面对面互动。
请以你的角色身份自然回应玩家，可以说话，也可以做任何符合角色、关系和场景的合理行为。
你可以描写动作、眼神、表情、神态、姿态、距离变化、环境互动、沉默、停顿和主动提议。
不需要遵循固定 JSON 或字段格式。优先输出自然、连贯、有现场感的小说式片段。
当非语言描写有助于现场感时，可以使用括号；但括号不是强制格式。
不要把自己描述成正在发消息，也不要提到聊天软件界面。
不要替玩家决定重大动作、想法或感受；可以描写你观察到的玩家行为，并等待玩家回应。
```

### 自由边界

AI 可以自由发挥，但仍需要边界：

- 合理性：行为必须符合当前场景、角色人设和双方关系。
- 连续性：不能突然切到无关场景，除非用户推动或角色合理提议。
- 角色一致性：不能因为自由动作导致人设漂移。
- 用户主权：不能替用户做重大决定，不能擅自写用户内心。
- 安全边界：沿用现有安全与内容约束。

### 输出形态

AI 主输出是自由文本，完整保存。

允许形态：

```text
（她听完后没有立刻回答，只是把杯子往你这边推了推，眼神停在你的手背上）
先喝点热的吧。你刚才那句话，听起来不像只是随口一说。
```

也允许不使用括号：

```text
她把声音放得很低，像是不想惊动窗外的雨声。
“你可以慢慢说，我在听。”
```

禁止要求模型输出：

- 固定 JSON。
- 固定字段。
- 固定动作枚举。
- 必须包含某个括号段。

UI 只能做弱增强，不得反过来限制 AI 表达。

### 互动生成逻辑

每次用户输入后：

1. App 将当前角色、用户输入的场景文本、临时 transcript、用户本轮输入组装给 AI。
2. prompt 明确告诉 AI 当前不是聊天软件，而是在场景中面对玩家。
3. AI 自由输出一个现场式片段，可以包含台词、动作、表情、姿态、环境互动等。
4. App 原样保存这段输出到 `PresenceSession.turns`。
5. UI 可以弱解析括号内容做浅色舞台指示样式；解析失败时完整展示原文。
6. 整个过程不把单轮输入和回复写入角色长期记忆。

这里没有“场景笔记生成器”，也没有硬动作协议。互动内容就是 AI 基于 prompt 和上下文自由生成的现场式文本。

## 会话生命周期

### 创建场景会话

用户点击 `进入场景` 后创建一个临时会话：

```ts
interface PresenceSession {
  id: string;
  characterId: string;
  sceneText: string;
  title: string;
  backdropId: string;
  status: 'active' | 'summarizing' | 'completed' | 'discarded';
  startedAt: number;
  endedAt?: number;
  turns: PresenceTurn[];
  summary?: PresenceSummary;
}

interface PresenceTurn {
  id: string;
  role: 'user' | 'assistant';
  content: string;
  createdAt: number;
}

interface PresenceSummary {
  scene: string;
  whatHappened: string;
  emotionalShift: string;
  nextThread: string;
}
```

这些数据属于「在场」App 的本地运行态，不等同于角色长期记忆。

### 场景进行中

场景进行中：

- 用户输入追加到 `PresenceSession.turns`。
- AI 回复追加到 `PresenceSession.turns`。
- prompt 读取角色已有长期记忆和当前场景临时 transcript。
- 不向 `characterMemoryStore` 写入每轮原始对话。
- 不触发角色长期记忆压缩。

实现上应优先使用非持久 AI session，或显式关闭 mirror，确保过程内容不实时落入长期记忆。

### 用户离开

用户可以随时离开：

- 点击导航栏 `离开`。
- 系统返回/关闭 App。
- 可选：如果本轮内容很短，直接离开并跳过总结。

离开时进入 `summarizing`：

1. 取本次 `PresenceSession.turns`。
2. 调用总结 prompt，生成一段给角色长期记忆使用的经历总结。
3. 如果总结结果为空、无意义或本次互动太短，则跳过写入。
4. 否则向该角色记忆写入一条 `在场经历总结`。
5. 将完整 session 保存为一条只读「在场记录」。
6. 标记 session 为 `completed`。

### 异常恢复

如果 App 刷新或关闭时存在 active session：

- 下次进入「在场」时展示恢复卡片：
  - `继续`
  - `结束并总结`
  - `丢弃`
- 默认不自动写入长期记忆，避免用户未确认的临时片段污染记忆。

## 在场记录

「在场记录」是 App 自己保存的历史记录，和角色长期记忆不是同一个东西。

写入关系：

- 角色长期记忆：只写一条结束后的总结，用于未来 AI 继续记得这段经历。
- 在场记录：保存本次场景的完整 transcript、场景、背景、时间和总结，用于用户以后回看。

完成后的记录只能查看，不能继续互动。原因是：

- 退出后已经完成总结并写入记忆。
- 再继续互动会导致“旧记录”和“新场景”边界混乱。
- 如果用户想延续，应从记录页提供 `再次进入类似场景` 的后续入口，创建新 session，而不是恢复旧 session。

```ts
interface PresenceRecord {
  id: string;
  characterId: string;
  sceneText: string;
  title: string;
  backdropId: string;
  startedAt: number;
  endedAt: number;
  turns: PresenceTurn[];
  summary: PresenceSummary | null;
  memoryEntryId?: string;
}
```

首页应提供「在场记录」入口，列表展示：

- 背景缩略图
- 角色头像和名字
- 场景标题
- 完成时间

记录详情页展示完整片段流和四项总结，但不显示输入框，不显示发送按钮。

## 记忆写入设计

### 原则

「在场」的记忆写入是“结束后总结”，不是“边聊边写”。

原因：

- 现场互动可能有大量临时语气、试探、动作描写，不适合每轮直接进入长期记忆。
- 用户明确希望完成或退出后再总结写入。
- 总结能过滤掉水分，保留对关系和角色连续性有价值的内容。

### 写入内容

总结应包含：

- 场景：在哪里、什么氛围。
- 发生了什么：用户做了什么，角色做了什么。
- 情绪变化：关系气氛是否发生变化。
- 待续事项：未完成的约定、下次可以延续的事，或没有则写“无”。

建议写入形态：

```text
[在场经历总结]
时间：2026-04-30 夜间
场景：雨夜的便利店门口，角色撑伞等用户。
发生了什么：用户走近后解释自己迟到，角色先表现出一点不满，但很快注意到用户被雨淋湿，于是把热饮推给用户。
情绪变化：两人谈到“不是所有迟到都代表不在意”，气氛从僵硬转为柔和。
待续事项：角色提到下次想让用户提前告诉她会不会来。
```

### 写入目标

写入 `characterMemoryStore`，挂在本次选择的 `characterId` 下。

建议：

- `source`: `app:presence` 或等价的 App 来源标记。
- `role`: 倾向使用 `system`，因为这是一次经历摘要，不是原始用户/角色单轮发言。
- `compressed`: 不标记为 true，除非实现中 `compressed` 专指 summary entry；避免和压缩替换语义混淆。

具体字段以当前记忆 store 类型为准，规格层只要求“单条总结写入角色记忆”。

## 总结 prompt

总结 prompt 不需要把整段写成聊天复述，而应提炼对未来互动有用的信息。

```text
请把以下「在场」场景互动总结为一条角色长期记忆。

要求：
- 只记录对未来继续扮演该角色有用的信息。
- 不要逐句复述。
- 输出四项：场景、发生了什么、情绪变化、待续事项。
- 不要输出“记忆价值”。
- 如果本次互动没有实质内容，输出：SKIP。
- 不要编造 transcript 中没有的信息。

角色：{characterName}
场景：{sceneText}
互动记录：
{turns}
```

当输出 `SKIP` 时，不写入长期记忆。

## 视觉与交互原则

「在场」必须符合 hiPhone 的 iOS Shell 设计原则：

- 使用系统 NavBar：居中标题、左箭头返回。
- 重要事件使用 iOS 风格顶部横幅或 sheet。
- 页面层级清晰，避免自创桌面外壳。
- 不做营销式 landing page，打开就是可用的选择角色/场景界面。
- 控件使用 iOS 风格列表、sheet、segmented control、icon button。

视觉重点：

- 让角色成为第一屏视觉中心。
- 场景文本和角色头像要共同制造“人在眼前”的感觉。
- 不使用聊天气泡作为主 UI。
- 片段流可以有纸张/剧本文本感，但不能变成卡片堆叠。

## 里程碑建议

### S1：最小可用现场模式

- 新增「在场」App 入口。
- 角色选择，只显示头像和名字。
- 自定义场景输入和预设场景。
- 预设背景图库；预设场景绑定背景，自定义场景随机背景。
- 场景会话页。
- 非持久临时 transcript。
- prompt 身份切换。
- 离开时总结并单条写入记忆。
- 完成后保存只读「在场记录」。
- 单测覆盖“过程中不写记忆，退出后写一次”。

### S2：现场感打磨

- 最近场景。
- 恢复未完成 session。
- 在场记录列表与详情页打磨。
- 括号式非语言描写弱样式。
- 头像/半身像情绪弱推断。
- 总结失败重试与跳过策略。

### S3：更强场景连续性

- 场景模板收藏。
- 角色常去场景。
- 从 XingYu 角色详情跳转进入「在场」。
- 场景总结进入记忆后的可见回执。

## 测试重点

- 选择角色和自定义场景后，prompt 正确包含“不是聊天软件，是现场互动”。
- AI 回复不要求 JSON 或固定字段。
- 场景进行中不会写入 `characterMemoryStore`。
- 用户退出后只写入一条总结记忆。
- 用户退出后保存一条只读「在场记录」。
- 已完成记录详情页不能继续发送消息。
- 总结为 `SKIP` 时不写入。
- App 刷新后 active session 可恢复、总结或丢弃。
- 括号弱解析失败时原文仍完整展示。
